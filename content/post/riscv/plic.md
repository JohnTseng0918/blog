## PLIC 是什麼

> The PLIC multiplexes various device interrupts onto the external interrupt lines of Hart contexts, with hardware support for interrupt priorities. PLIC supports up-to 1023 interrupts (0 is reserved) and 15872 contexts, but the actual number of interrupts and context depends on the PLIC implementation. However, the implementation must adhere to the offset of each register within the PLIC operation parameters.

- PLIC 把各種裝置的中斷「多工」到 hart context 的 external interrupt line 上,並在硬體層提供 priority 支援
- 規格上限:**1023 個 interrupt**(ID 0 保留)、**15872 個 context**
- 實際支援幾個 interrupt / context 由實作決定,但**每個 register 的 offset 必須遵守規格**
  - 所以 memory map 的邊界是照上限算出來的:priority 到 `0x000FFC`(source 1023)、enable bits 到 `0x1F1FFC`(context 15871)、threshold 與 claim/complete 到 `0x3FFF000`/`0x3FFF004`(context 15871)

## Interrupt target 與 hart context

**hart context**:a given privilege mode on a given hart(某個 hart 上的某個特權模式)

- 在一個 4-core 且 2-way SMT 的系統中,硬體上會有 8 個 hart
- 如果每個 hart 都支援 machine mode(M-mode)和 supervisor mode(S-mode)這兩種特權模式,那麼整個系統中就會有至少 16 個 hart context

> Not all hart contexts need be interrupt targets, in particular, if a processor core does not support delegating external interrupts to lower-privilege modes, then the lower-privilege hart contexts will not be interrupt targets. Interrupt notifications generated by the PLIC appear in the meip/seip bits of the mip/sip registers for M/S modes respectively.

- 並非所有的 hart context 都會被當作中斷目標(interrupt target)
- 如果某個 core 不支援把 external interrupt 委派(delegate)給低特權模式,那麼該 hart 上的低特權 hart context(如 S-mode)就不會被列為 PLIC 的中斷目標
- PLIC 產生的 interrupt notification 分別出現在 `mip`/`sip` 的 `meip`/`seip` 位元

> Each processor core must define a policy on how simultaneous active interrupts are taken by multiple hart contexts on the core.

- 多個 hart context 同時收到中斷時,如何排定優先順序是由 core 的設計政策決定的

> The PLIC treats each interrupt target independently and does not take into account any interrupt prioritization scheme used by a component that contains multiple interrupt targets. As a result, the PLIC provides no concept of interrupt preemption or nesting so this must be handled by the cores hosting multiple interrupt target contexts.

- PLIC 把每一個 interrupt target 視為完全獨立的個體
- PLIC 內部不提供中斷搶佔(preemption)或巢狀中斷(nesting)的概念,這要由 core 自己處理

## Interrupt gateway

> The interrupt gateways are responsible for converting global interrupt signals into a common interrupt request format, and for controlling the flow of interrupt requests to the PLIC core.

- gateway 負責把各種 global interrupt signal 轉成統一的 interrupt request 格式,並控制送往 PLIC core 的流量

> At most one interrupt request per interrupt source can be pending in the PLIC core at any time, indicated by setting the source's IP bit.
>
> The gateway only forwards a new interrupt request to the PLIC core after receiving notification that the interrupt handler servicing the previous interrupt request from the same source has completed.

- 在任何時間點,同一個 interrupt source 在 PLIC core 中最多只能有一個 pending 的請求(即其 IP bit 被設為 1)
- gateway 只有在收到該 source 的 interrupt completion 訊息後,才會向 PLIC core 轉發下一個新的 interrupt request

### Level-sensitive

- gateway 會把 interrupt signal 的**第一次 assert** 轉換成單一 interrupt request 送給 PLIC core(把 IP bit 設為 1)
- 一旦送出請求,gateway 就不會再送新的請求,直到它收到來自 target 的 interrupt completion 訊息
- 收到 completion 時,gateway 會再看一次訊號線,如果還處於 asserted 狀態,就立刻向 PLIC core 送出下一個新請求
- 如果 interrupt source 在 PLIC core 已接受請求之後、handler 實際服務之前就 deassert,這個 request 不會消失,它依然 latch 在 PLIC core 的 IP bit 中並觸發 handler
  - gateway 沒有能力把已經送出的 request 收回,所以 handler 必須自己判斷該裝置是不是已經不需要服務

### Edge-triggered

- gateway 會把捕捉到的**第一個 matching edge** 轉換成 interrupt request 送給 PLIC core
- 處理期間又來的 edge,依硬體實作可以有兩種行為:
  - **ignore**:直接忽略這段期間發生的新 edge
  - **pending interrupt counter**:用一個內部 counter 記錄 pending 的中斷次數,當 PLIC core 接受下一個請求時 counter 遞減
- 不論哪種實作,下一筆 interrupt request 都不會在收到前一筆的 completion 訊息之前被送給 PLIC core

### Message-signalled interrupts(MSI)

- MSI 不像傳統中斷有專門的實體訊號線,而是透過 system interconnect 送出帶有中斷資訊的 message packet
- packet 被解碼、選出對應的 gateway 之後,gateway 會以類似 **edge-triggered** 的方式處理這個 MSI

## Interrupt notification

> Each interrupt target has an external interrupt pending (EIP) bit in the PLIC core that indicates that the corresponding target has a pending interrupt waiting for service.

- PLIC core 中每一個 interrupt target(通常是某個 hart context)都有一個專屬的 EIP bit,用來指示該 target 目前是否有 external interrupt 正在等待服務

> The value in EIP can change as a result of changes to state in the PLIC core, brought on by interrupt sources, interrupt targets, or other agents manipulating register values in the PLIC. The value in EIP is communicated to the destination target as an interrupt notification.

- EIP 的值會隨 PLIC core 內部狀態變化而更新,觸發來源可能是 interrupt source 送新請求、target 執行 claim/completion,或其他 agent 直接改 PLIC 的 register
- EIP 的值會以 interrupt notification 的形式傳給對應的 target

> If the target is a RISC-V hart context, the interrupt notifications arrive on the meip/seip bits depending on the privilege level of the hart context.

> In simple systems, the interrupt notifications will be simple wires connected to the processor implementing a hart.
> In more complex platforms, the notifications might be routed as messages across a system interconnect.

## Multicast

> The PLIC hardware only supports multicasting of interrupts, such that all enabled targets will receive interrupt notifications for a given active interrupt.

- 優點:能提供極快的響應速度,因為執行速度最快的 target 會搶先 claim 並處理該中斷
- 缺點(資源浪費):在高頻率中斷的場景下,可能會導致多個 hart 同時進入中斷處理流程,但最終卻只有一個 hart 能成功 claim,其餘 core 的調度便白白浪費了
- 軟體調控方案:規格書指出,軟體可以透過在 handler 中調度 PLIC 的 IE(interrupt enable)bit,來實作更靈活的策略,例如 interrupt affinity 或 round-robin unicasting

## Interrupt ID

> Global interrupt sources are assigned small unsigned integer identifiers, beginning at the value 1.
> An interrupt ID of 0 is reserved to mean "no interrupt".
>
> Interrupt identifiers are also used to break ties when two or more interrupt sources have the same assigned priority. Smaller values of interrupt ID take precedence over larger values of interrupt ID.

- interrupt ID 從 1 開始,0 保留代表「沒有中斷」
- 同 priority 時用 interrupt ID 決勝負,ID 越小優先權越高

## Interrupt flow

1. Global interrupts are sent from their source to an interrupt gateway that processes the interrupt signal from each source
2. Interrupt gateway then sends a single interrupt request to the PLIC core, which latches these in the core interrupt pending bits (IP)
3. The PLIC core forwards an interrupt notification to one or more targets if the targets have any pending interrupts enabled, and the priority of the pending interrupts exceeds a per-target threshold
4. When the target takes the external interrupt, it sends an interrupt claim request to retrieve the identifier of the highest priority global interrupt source pending for that target from the PLIC core
5. PLIC core then clears the corresponding interrupt source pending bit
6. After the target has serviced the interrupt, it sends the associated interrupt gateway an interrupt completion message
7. The interrupt gateway can now forward another interrupt request for the same source to the PLIC

## Register

| Register block | 功能 |
| --- | --- |
| Interrupt Priorities | The interrupt priority for each interrupt source |
| Interrupt Pending Bits | The interrupt pending status of each interrupt source |
| Interrupt Enables | The enablement of interrupt source of each context |
| Priority Thresholds | The interrupt priority threshold of each context |
| Interrupt Claim | The register to acquire interrupt source ID of each context |
| Interrupt Completion | The register to send interrupt completion message to the associated gateway |

### Interrupt Priorities

> Interrupt priorities are small unsigned integers, with a platform-specific maximum number of supported levels.
> The priority value 0 is reserved to mean "never interrupt", and interrupt priority increases with increasing integer values.

- priority 是 small unsigned integer,數值越大優先權越高
- 每個 interrupt source 各自有一個 32-bit 的 memory-mapped `priority` register,寫進去就是設定該 source 的 priority
- **0 是保留值,代表 never interrupt**,效果等同於 disable 這個中斷
- 最低的有效 priority 是 1,能支援到多大則取決於 PLIC 的實作

> Ties between global interrupts of the same priority are broken by the Interrupt ID; interrupts with the lowest ID have the highest effective priority.

- 當兩個以上 pending 的 interrupt source 有相同 priority 時,PLIC core 用 interrupt ID 決勝負
- interrupt ID 越小,effective priority 越高

### Interrupt Pending Bits

> The current status of the interrupt source pending bits in the PLIC core can be read from the pending array, organized as 32-bit register.
> The pending bit for interrupt ID N is stored in bit (N mod 32) of word (N/32). Bit 0 of word 0, which represents the non-existent interrupt source 0, is hardwired to zero.

- interrupt ID N 的 pending bit 位在 word `N/32` 的 bit `N mod 32`
- word 0 的 bit 0 對應不存在的 interrupt source 0,hardwired 為 0
- 整個 pending 區塊是連續的記憶體空間,大小 128 bytes(`0x80`):每個 source 佔 1 bit,1024 bits 剛好對應 ID 0 ~ 1023(扣掉保留的 0 號,實際可用 1023 個)

> A pending bit in the PLIC core can be cleared by setting the associated enable bit then performing a claim.

- 要清掉某個 pending bit,必須在對應的 enable bit 有拉起來的情況下,由 interrupt target 發出 claim

### Interrupt Enables

> Each global interrupt can be enabled by setting the corresponding bit in the enables register.
> The enables registers are accessed as a contiguous array of 32-bit registers, packed the same way as the pending bits.

- enable bits 用來控制哪些 interrupt source 可以向特定的 context 送出中斷
- 排放方式和 pending bits 一樣,只是每個 context 都有一整組

```text
0x002000: Interrupt Source #0   to #31   Enable Bits on context 0
...
0x00207C: Interrupt Source #992 to #1023 Enable Bits on context 0
0x002080: Interrupt Source #0   to #31   Enable Bits on context 1
...                                                   以此類推
0x1F1FFC: Interrupt Source #992 to #1023 Enable Bits on context 15871
```

### Priority Thresholds

> PLIC provides context based threshold register for the settings of a interrupt priority threshold of each context. The threshold register is a WARL field. The PLIC will mask all PLIC interrupts of a priority less than or equal to threshold. For example, a threshold value of zero permits all interrupts with non-zero priority.

- 每個 context 各自有一個 threshold register(WARL field)
- PLIC 會 mask 掉所有 priority **小於或等於** threshold 的中斷,只有嚴格大於 threshold 的中斷才會送出 interrupt notification
- 所以 threshold 設 0 = 放行所有 priority 非 0 的中斷

### Interrupt Claim Process

> Sometime after a target receives an interrupt notification, it might decide to service the interrupt.
> The target sends an interrupt claim message to the PLIC core, which will usually be implemented as a non-idempotent memory-mapped I/O control register read.
> On receiving a claim message, the PLIC core will atomically determine the ID of the highest-priority pending interrupt for the target and then clear down the corresponding source's IP bit.
> The PLIC core will then return the ID to the target. The PLIC core will return an ID of zero, if there were no pending interrupts for the target when the claim was serviced.

- interrupt target 去讀自己 context 的 claim/complete register(MMIO),這是一個 **non-idempotent** 的讀取,每讀一次就會改變 PLIC core 的內部狀態
- PLIC core 收到 claim 後,會 atomically 決定該 target 目前 pending 中 priority 最高的 interrupt ID,清掉對應 source 的 IP bit,再把 ID 回傳給 hart
  - 回傳 0 代表沒有 pending 的中斷

> After the highest-priority pending interrupt is claimed by a target and the corresponding IP bit is cleared, other lower-priority pending interrupts might then become visible to the target, and so the PLIC EIP bit might not be cleared after a claim. The interrupt handler can check the local meip/seip/ueip bits before exiting the handler, to allow more efficient service of other interrupts without first restoring the interrupted context and taking another interrupt trap.

- 最高優先權的中斷被 claim 之後,其他較低優先權的 pending interrupt 可能就對這個 target 變成可見,所以 claim 完 EIP 不一定會被清掉
- 因此 handler 在離開前可以順手檢查 local 的 `meip`/`seip` bit:如果還是 1 就直接在同一次 trap 裡繼續處理下一個中斷,不必先還原被打斷的 context、再吃一次 interrupt trap

> It is always legal for a hart to perform a claim even if the EIP is not set. In particular, a hart could set the threshold value to maximum to disable interrupt notifications and instead poll for active interrupts using periodic claim requests, though a simpler approach to implement polling would be to clear the external interrupt enable in the corresponding xie register for privilege mode x.

- **EIP 沒被設起來時,hart 一樣可以合法地做 claim**
- 所以 polling 是可行的:把 threshold 設到最大來關掉 interrupt notification,改成定期發 claim 去撈有沒有 active interrupt
- 不過規格書也說,要做 polling 更簡單的做法是直接清掉對應特權模式的 `xie` 中的 external interrupt enable(即 `mie.MEIE`/`sie.SEIE`)

> The PLIC can perform an interrupt claim by reading the claim/complete register, which returns the ID of the highest priority pending interrupt or zero if there is no pending interrupt. A successful claim will also atomically clear the corresponding pending bit on the interrupt source.
> The PLIC can perform a claim at any time and the claim operation is not affected by the setting of the priority threshold register.

- claim 隨時都可以做,而且**不受 priority threshold 影響**

### Interrupt Completion

> The PLIC signals it has completed executing an interrupt handler by writing the interrupt ID it received from the claim to the claim/complete register.

- 把 claim 時拿到的 interrupt ID 寫回 claim/complete register,藉此告知 PLIC 這個中斷處理完了

> The PLIC does not check whether the completion ID is the same as the last claim ID for that target.
> If the completion ID does not match an interrupt source that is currently enabled for the target, the completion is silently ignored.

- PLIC 不會檢查 completion ID 和上一次的 claim ID 是否相同
- 如果 completion ID 對不到該 target 目前 enable 的 interrupt source,這次 completion 會被靜靜忽略

> After a handler has completed service of an interrupt, the associated gateway must be sent an interrupt completion message, usually as a write to a non-idempotent memory-mapped I/O control register.
> The gateway will only forward additional interrupts to the PLIC core after receiving the completion message.

- gateway 收到 completion 訊息後,才會再把同一個 source 的下一筆中斷轉發給 PLIC core
